---

## 1. Purpose

KTS-I4-D defines the first evidence and memory foundation for the Construct Intelligence Harness.

The slice establishes:

- immutable evidence records;
- cryptographic content integrity;
- explicit provenance and lineage;
- contradiction-preserving relations;
- bounded working memory;
- immutable episodic memory;
- deterministic retrieval;
- storage-neutral repository contracts;
- an append-only in-memory conformance repository;
- a production-oriented Cloudflare D1 repository adapter;
- a versioned D1 migration;
- a Keep the Signal observation-to-evidence adapter.

This is the first slice permitted to design durable memory storage.

It does not yet:

- invoke a model;
- construct tactical prompts;
- generate tactical recommendations;
- validate or execute model proposals;
- write from the live KTS runtime;
- create semantic claims;
- promote procedural skills;
- consolidate memories;
- delete memories;
- create tombstones;
- generate training examples;
- train or fine-tune;
- provision a remote D1 database;
- modify Wrangler bindings;
- deploy anything.

KTS-I4-D records and retrieves evidence. It does not decide strategy.

## 2. Architectural position

```text
Accepted authoritative domain evidence
    ↓ domain adapter
Immutable evidence draft
    ↓ validation + canonicalization + SHA-256
Evidence and provenance ledger
    ↓ explicit relations
Working and episodic memory fabric
    ↓ bounded deterministic retrieval
Future KTS-I4-E tactical adviser
```

The evidence ledger and memory fabric are transferable harness infrastructure.

The Keep the Signal adapter is domain-specific and may only translate accepted KTS observation packets into generic evidence drafts.

## 3. Permanent authority boundaries

### 3.1 Domain authority

The memory fabric may store accepted facts about a domain.

It may not:

- mutate authoritative domain state;
- infer that a proposed action was legal without authoritative evidence;
- alter an outcome;
- overwrite an accepted domain digest;
- repair invalid domain evidence;
- create gameplay events;
- call `stepGame`;
- call `runSimulation`.

### 3.2 Evidence authority

An evidence record is a preserved assertion about supplied source material.

The memory fabric must distinguish:

- source evidence;
- derived evidence;
- inference;
- correction;
- contradiction;
- governance decision;
- outcome evidence.

A memory record may reference evidence. It may not become evidence merely because it was retrieved frequently or generated by a model.

### 3.3 Human and governance authority

The memory fabric may not:

- promote candidate knowledge into accepted strategy;
- remove protected records;
- weaken retention requirements;
- conceal contradictory evidence;
- grant access to a classification not explicitly permitted;
- create or alter authorization rules;
- provision or deploy infrastructure.

## 7. Canonical JSON

Every persisted digest-bearing record must use one canonical JSON implementation.

Required behaviour:

- accept JSON-compatible primitives, arrays, and plain records;
- reject `undefined`, functions, symbols, bigint, class instances, non-finite numbers, and cycles;
- sort record keys lexicographically;
- preserve array order;
- preserve string values exactly;
- encode numbers using JSON-compatible finite-number representation;
- return byte-identical text for equivalent records;
- never depend on object insertion order;
- never include platform-specific values.

Canonicalization must be domain-independent.

---

## 8. Cryptographic digest

KTS-I4-D introduces the first cryptographic evidence digest.

Required algorithm:

```text
SHA-256
```

Required representation:

```text
64 lowercase hexadecimal characters
```

The implementation must:

- digest UTF-8 canonical JSON bytes;
- use a platform-standard cryptographic implementation;
- contain no hidden randomness;
- expose asynchronous digest creation;
- verify supplied digests using constant-shape comparison where practical;
- reject malformed digests before repository operations.

The digest must not replace the accepted KTS source-state digest.

For a KTS observation:

- `sourceStateDigest` remains the accepted engine provenance field;
- `contentDigest` is the SHA-256 digest of the immutable evidence content.

## 9. Identity

All public identities are caller supplied.

Required identity classes:

- evidence ID;
- relation ID;
- memory ID;
- working-memory item ID;
- repository operation ID;
- optional episode ID;
- optional session ID;
- optional model, strategy, evaluator, or actor ID when such evidence exists later.

Identity rules:

- non-empty;
- 1 to 160 characters;
- begins with an ASCII alphanumeric character;
- contains only ASCII alphanumeric characters plus `.`, `_`, `:`, and `-`;
- no whitespace;
- no hidden random generation;
- no wall-clock-derived identity;
- no database-generated authoritative identity.

Database row ordering may use internal implementation details, but those values must not become public record identity.

## 10. Supplied time and authoritative position

The core must not call `Date.now()`.

Every persisted record must receive an explicit caller-supplied `recordedAt` value using canonical UTC:

```text
YYYY-MM-DDTHH:mm:ss.sssZ
```

The record may also contain an authoritative domain position.

For KTS this includes:

- seed;
- tick;
- source-state digest.

Generic authoritative positions must be JSON-compatible and versioned.

Repository ordering must never silently substitute database insertion time for authoritative domain position.

## 12. Evidence digest envelope

The content digest must cover the complete immutable evidence content except:

- `evidenceId`;
- `contentDigest`.

The digest input must include:

- domain identity;
- source type and source schema;
- source identity;
- authoritative position;
- payload;
- acceptance state;
- classification;
- retention class;
- tags;
- recorded-at time;
- actor identity when present;
- operation identity when present.

This prevents classification, status, retention, provenance, or payload changes from preserving the same digest.

Required relation fields:

- relation ID;
- relation type;
- source evidence ID;
- target evidence ID;
- relation schema version;
- optional JSON metadata;
- recorded-at time;
- optional actor ID;
- optional operation ID.

Required relation types:

```text

```

Rules:

- source and target must exist;
- self-relations are rejected;
- duplicate relation IDs are idempotent only when byte-equivalent;
- a duplicate relation ID with different content fails;
- `derived_from`, `corrects`, and `supersedes` relations must not introduce a lineage cycle;
- contradiction relations must be preserved and retrievable;
- a contradiction must not automatically suppress either evidence record.

## 14. Duplicate and collision semantics

Repository writes must be idempotent.

For evidence, memory, and relation records:

- same ID plus byte-equivalent canonical content returns the existing record;
- same ID plus different canonical content fails with an identity-collision error;
- no partial write may remain after a failed compound operation;
- digest mismatch fails before persistence;
- repository implementations must return immutable clones.

Content duplicates with different IDs are permitted and must remain distinguishable by provenance.

## 15. Working memory

Working memory is bounded, temporary, and non-authoritative.

It is not persisted by KTS-I4-D.

Required item kinds:

```text
observation
instruction
inference
retrieved_memory
evidence_reference
```

Every item must include:

- item ID;
- item kind;
- sequence;
- priority;
- required flag;
- source identity;
- JSON-compatible content;
- optional evidence references;
- serialized-character count.

Working-memory budgets must include:

- maximum item count;
- maximum serialized characters;
- maximum retrieved-memory items;
- maximum evidence references.

Deterministic packing order:

1. required items;
2. higher priority;
3. lower sequence;
4. lexicographically lower item ID.

Required items must never be silently omitted.

If required items exceed a budget, assembly fails.

Omitted optional items must be reported with reasons.

The output must distinguish source observation, instruction, inference, and retrieved memory.

## 20. Retrieval policy

Every retrieval request must contain:

- request ID;
- allowed domains;
- allowed classifications;
- accepted retention classes;
- result limit;
- serialized-character budget;
- relation traversal limit;
- optional exact identities;
- optional source or memory types;
- optional acceptance states;
- optional tags;
- optional time range;
- optional authoritative-position range;
- optional lineage or contradiction relation filters.

Safe defaults:

- no domain is implicitly allowed;
- no classification is implicitly allowed;
- result limit is not silently increased;
- relation traversal is zero unless requested;
- unsupported semantic search fails rather than degrading to a misleading substitute.

## 21. Deterministic retrieval

Initial supported retrieval views:

- exact identity;
- typed metadata;
- domain and version;
- source or memory kind;
- acceptance state;
- classification and retention;
- tags;
- recorded-at range;
- authoritative KTS tick range;
- direct lineage;
- direct contradiction;
- direct evidence attachment.

Semantic similarity, embeddings, causal inference, and learned ranking are deferred.

Stable result ordering:

1. authoritative domain position descending when comparable;
2. recorded-at time descending;
3. identity ascending.

When authoritative positions are not comparable, use:

1. recorded-at time descending;
2. identity ascending.

Truncation must be visible.

The repository must report:

- source match count when available within budget;
- returned count;
- omitted count when knowable;
- truncation state;
- applied filters;
- ordering policy;
- serialized-character usage.

---

## 22. Retrieval security

The repository must enforce the request allowlists.

A record whose classification is not allowed must not appear in:

- results;
- counts;
- relation traversal;
- error diagnostics;
- omission metadata that reveals its existence.

Restricted data must therefore fail closed.

KTS-I4-D does not implement user authentication, but repository callers cannot bypass explicit classification filtering.

## 23. In-memory conformance repository

The in-memory repository is a permanent reference and test implementation.

It must:

- implement the complete repository contract;
- preserve append-only semantics;
- implement idempotency and collision behaviour;
- clone and freeze all inputs and outputs;
- support deterministic bounded retrieval;
- support relation-cycle checks;
- preserve contradictions;
- contain no global singleton;
- support explicit disposal;
- clear its private state only on disposal;
- never be described as durable persistence.

It is not a throwaway prototype.

It is the executable conformance oracle for storage adapters and deterministic experiments.

---

## 24. Cloudflare D1 adapter

The D1 adapter is a production-oriented durable repository implementation.

It must:

- receive a D1-compatible database binding through dependency injection;
- contain no global binding lookup;
- use prepared statements and bound parameters;
- use transactions or D1 batch semantics for compound writes;
- preserve idempotency and collision rules;
- enforce bounded queries;
- verify JSON and digest fields at the boundary;
- reconstruct immutable public records;
- fail closed on unexpected rows;
- avoid logging payloads;
- avoid network APIs other than the injected D1 binding;
- avoid Node filesystem or process APIs;
- remain testable through a D1-compatible injected driver.

KTS-I4-D does not modify `wrangler.jsonc`.

No fake production database identifier may be committed.

Remote D1 resource creation and binding activation require a separate operator-authorized infrastructure step.

## 29. Deterministic concurrency

Repository operations must define deterministic collision behaviour under concurrent writes.

Required rule:

- first successfully committed canonical record for an identity wins;
- a concurrent byte-equivalent write succeeds idempotently;
- a concurrent non-equivalent write fails as `identity_collision`.

Compound episode insertion and evidence attachment must be atomic.

No partial episode may be visible.

The in-memory repository must serialize mutation operations internally without relying on wall-clock timing.

The D1 adapter must use database transaction or batch semantics.
