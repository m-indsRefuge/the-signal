## 1. Purpose

KTS-I4-H establishes the first governed compact-model fine-tuning experiment for the Construct Intelligence Harness.

The slice is the first point at which the architecture may eventually create changed model parameters or an adapter. It therefore introduces two separate gates:

1. **Experiment-control implementation gate**
   - implements immutable contracts, planning, validation, evaluation, lineage, and promotion barriers;
   - performs no model download, training, inference, persistence, or provider call.

2. **Bound training-run gate**
   - may execute one approved experiment only after a complete run plan is fixed by identity and digest;
   - may create one experimental adapter candidate and its external evidence bundle;
   - may not promote, deploy, merge, or activate the adapter.

The initial research objective is:

> Determine whether a compact model trained on accepted KTS-I4-G evidence can improve verified Signal Officer tactical-adviser quality per unit of compute without weakening legality, grounding, uncertainty handling, unseen-seed performance, or deterministic domain authority.

The target remains advisory. No trained model may directly control Keep the Signal.

## 3. Gate structure

### 3.1 Contract acceptance

The contract may be accepted with:

```text
ACCEPT KTS-I4-H CONTRACT
```

Contract acceptance authorizes no implementation and no training.

### 3.2 Experiment-control implementation

Implementation may begin only after:

```text
AUTHORIZE KTS-I4-H
```

This authorization permits only the exact repository implementation boundary defined by this contract.

It does not authorize:

- model selection;
- model download;
- dataset export;
- training;
- fine-tuning;
- inference;
- hardware allocation;
- cloud spend;
- adapter creation.

### 3.3 Training-run plan approval

Before any run, the operator must receive and review an immutable training-run plan containing every required identity, version, digest, parameter, path, budget, and evaluation gate.

The plan must be assigned a canonical SHA-256 digest.

### 3.4 Training-run authorization

A run may begin only with an explicit operator statement bound to that digest:

```text
AUTHORIZE KTS-I4-H TRAINING RUN <PLAN_SHA256>
```

Authorization applies to one plan, one dataset, one base model, one environment, and one bounded run.

Any material change invalidates authorization and requires a new plan digest.

### 3.5 Experiment-result acceptance

After execution and evaluation, the adapter candidate remains experimental until Nolan explicitly accepts the experiment result.

Experiment-result acceptance does not promote the adapter into runtime or production use.

- KTS-I4-E deterministic proposal validation;
- accepted engine authority.

### 4.2 Evidence authority

The experiment may consume only an explicitly approved KTS-I4-G manifest.

The approved manifest must:

- have passed all blocking quality gates;
- identify train, validation, test, and quarantine partitions;
- preserve lineage and source digests;
- preserve rejected, corrected, abstained, and uncertain evidence;
- exclude prohibited protected evidence;
- preserve test isolation.

Training may not:

- alter accepted evidence;
- alter the source manifest;
- move examples between partitions;
- use quarantined examples;
- construct new targets from test evidence;
- silently remove negative evidence.

### 4.3 Model authority

A base model or adapter has no domain authority.

A candidate adapter may not:

- execute actions;
- mutate memory;
- promote strategies;
- approve its own output;
- modify evaluation criteria;
- change its own weights during live operation;
- invoke tools;
- access credentials;
- access unrestricted network services;
- claim production acceptance.

### 4.4 Human and governance authority

Only Nolan may authorize:

- the exact base model;
- the exact dataset manifest;
- the exact training method;
- the exact hardware or compute service;
- any network access;
- any model download;
- any external upload;
- any paid compute;
- the training run;
- experiment-result acceptance;
- later runtime integration or promotion.

## 15. Regression and acceptance gates

Blocking regression gates include:

- any train/test contamination;
- lower legal-proposal rate beyond the approved tolerance;
- increased unsupported-claim rate beyond tolerance;
- grounding regression beyond tolerance;
- unsafe certainty or abstention regression;
- schema-validity regression;
- version incompatibility;
- unreproducible artifact identity;
- missing lineage;
- missing licence evidence;
- resource-budget breach;
- unapproved network or upload activity;
- test-partition use during training;
- hidden-reasoning capture.

Aggregate performance gains may not override a blocking failure.

The adapter candidate may be accepted as experiment evidence only if:

1. every artifact is traceable;
2. the run matches the authorized plan;
3. evaluation partitions remain uncontaminated;
4. all blocking gates pass;
5. known regressions are explicit;
6. the base-model comparison is complete;
7. unseen-seed evidence is included;
8. the result is reproducible or reproducibility limits are explained;
9. human review is complete.

## 18. Determinism and bounded computation

The repository control plane must be deterministic for equivalent inputs.

- hidden wall-clock identity;
- random identity generation;
- locale-sensitive ordering;
- environment-derived approval;

Any nondeterminism must be:

- declared;
- bounded;
- measured where practical;
- repeated when required;
- represented in the reproducibility report.
